한 줄 요약

Atome에서 가져온 MVP를 GitHub에서 직접 개발 가능한 React/Vite/Supabase 프로젝트로 정리했고, 관리자 가입/승인, 기관 등록 필드, 기관 승인/거절, 관리자별 데이터 제한의 기초 흐름까지 구현했습니다.

1. 처음 상태와 문제

처음 저장소에는 실제 개발용 소스 코드가 정상 폴더 구조로 존재하지 않았습니다. 초기에는 ZIP 파일 또는 잘못 업로드된 파일들이 있었고, GitHub 웹 업로드 과정에서 파일명과 파일 내용이 서로 맞지 않는 문제가 발생했습니다.

문제상세 내용처리 결과
ZIP 단일 파일원본 MVP가 압축파일 형태로만 존재해 GitHub에서 코드 리뷰/실행/배포가 어려웠습니다.원본 ZIP을 기준으로 정상 프로젝트 구조로 전환했습니다.
잘못된 수동 업로드파일들이 루트에 흩어지거나 파일명과 내용이 꼬이는 상황이 있었습니다.잘못 올라간 파일을 삭제하고 원본 ZIP에서 다시 정리했습니다.
Atome/MGX 의존Atome에서 생성한 개발용 도구와 메타데이터가 남아 있었습니다.앱 본 기능과 무관한 Atome/MGX 도구는 제거했습니다.

2. 현재 프로젝트 구조

현재 GitHub main은 일반적인 Vite 프로젝트 구조입니다.

.
├── package.json
├── index.html
├── vite.config.ts
├── src/
│   ├── App.tsx
│   ├── main.tsx
│   ├── contexts/

│   ├── pages/
│   └── components/

├── public/

└── README.md

이 구조 덕분에 앞으로는 Atome ZIP을 다시 풀지 않고 GitHub 코드 기준으로 바로 개발할 수 있습니다.

3. 제거한 항목

아래 항목들은 MVP의 실제 서비스 기능이 아니라 Atome/MGX 생성 환경 또는 미사용 코드로 판단되어 제거했습니다.

제거 항목이유
.atoms/Atome 내부 메타데이터 성격
.mgx/MGX/Atome 생성 환경 설정
@metagptx/*서비스 실행에 필수적이지 않은 생성 도구 의존성
@playwright/mcp앱 런타임과 직접 관련 없는 도구 의존성
Atome Vite 플러그인일반 Vite 앱 운영에는 불필요
AuthCallback, api.ts현재 라우팅/인증 흐름에서 사용되지 않음

주의: 앱의 주요 페이지, Supabase 인증, 관리자 기능, 기관/문의/예약 관련 코드는 유지했습니다.

6. 환경변수와 Supabase 연결

GitHub에는 실제 비밀값을 올리지 않았습니다. 대신 .env.example만 유지합니다.

VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=

로컬 실행 시에는 실제 값을 가진 .env가 필요합니다. 이 값이 없으면 Supabase client 생성 단계에서 supabaseUrl is required 오류가 발생할 수 있습니다.

보고서에는 Supabase 키, 비밀번호 등 민감정보를 포함하지 않았습니다.

기존 /admin-login, /admin-signup, /admin 경로는 새 경로로 redirect되도록 유지했습니다.

8. 관리자 가입/승인 흐름

  1. 관리자는 /admin/signup에서 가입합니다.
  2. 가입 시 role = admin으로 프로필이 생성됩니다.
  3. 가입 직후 is_approved = false입니다.
  4. 대표관리자가 관리자 탭에서 승인합니다.
  5. 승인된 관리자만 /admin/dashboard에 접근할 수 있습니다.

대표관리자 계정으로 실제 로그인 테스트를 수행했고, super_admin 권한과 대시보드 접근을 확인했습니다.

9. 관리자 로그인 버그 수정

로그인 직후 프로필을 다시 불러오는 짧은 시간 동안 isAdmin=false로 판단되어 관리자 대시보드에서 로그인 화면으로 튕길 수 있는 문제가 있었습니다.

문제수정
로그인 직후 profile loading 중 redirect 발생 가능auth state change에서 session user가 있으면 setLoading(true) 후 profile 로딩 완료 시 false 처리

수정 후 실제 대표관리자 로그인 → /admin/dashboard 로딩을 확인했습니다.

10. Supabase 테이블/필드 변경

사용자가 Supabase Dashboard에서 기관 테이블에 아래 필드를 추가했습니다. 이후 코드 타입과 관리자 폼을 맞춰 수정했습니다.

테이블필드타입목적
institutionsstatustext기관 승인 상태: pending / approved / rejected
institutionscreated_byuuid기관을 등록한 관리자 profile id
institutionsbusiness_notext사업자 등록 번호
institutionsinst_notext기관 고유 번호
institutionsmanager_nametext담당자 이름 및 연락처

현재 DB 필드는 Supabase Dashboard에서 수동으로 추가했습니다. 장기적으로는 SQL migration 파일로 관리하는 것이 좋습니다.

11. 기관 등록 폼 변경

관리자 대시보드의 기관 등록/수정 폼에 아래 입력란을 추가했습니다.

  • 사업자 등록 번호
  • 기관 고유 번호
  • 담당자 이름 및 연락처

새 기관 등록 시 저장되는 값:

status = 'pending'
created_by = 현재 관리자 profile.id
business_no = 입력값
inst_no = 입력값
manager_name = 입력값

12. 기관 승인/거절 기능

대표관리자가 기관 목록에서 승인 상태를 변경할 수 있도록 했습니다.

상태화면 의미가능 액션
pending승인대기승인 또는 거절
approved승인거절로 변경 가능
rejected거절승인으로 변경 가능

승인/거절 액션은 관리자 활동 로그에 기록됩니다.

13. 관리자별 데이터 제한

일반 관리자는 자신이 등록한 기관만 관리하도록 프론트엔드 조회 로직을 제한했습니다.

역할현재 접근 범위
일반 관리자created_by = 본인 profile.id인 기관만 조회
일반 관리자본인 기관과 연결된 문의만 조회
일반 관리자본인 기관과 연결된 예약만 조회
일반 관리자관리자/사용자 전체 목록은 보지 않음
일반 관리자전체 삭제도 본인 기관 범위로 제한
대표관리자전체 기관, 전체 문의, 전체 예약, 전체 관리자, 전체 로그 조회

중요: 이 제한은 현재 프론트엔드 중심입니다. 실제 보안을 위해 Supabase RLS가 반드시 필요합니다.
